# Firmware on the current robot

The ESP32-S3 firmware starts at `Slave/firmware/esp32s3/main/app_main.c`.
It connects the shared C body core to ESP-IDF services. The core checks commands,
tracks their state, and enforces motion safety. The platform code handles
FreeRTOS tasks, networking, NVS storage, filesystems, GPIO, PWM, camera, display,
and audio.

Portable-core tests check those command rules separately from the physical
controller. The former simulator has been retired.

## Hardware and build

The current target is **ESP-IDF 5.5.4 on ESP32-S3 N16R8**, with:

- 16 MB flash and 8 MB octal PSRAM at 80 MHz;
- two 3 MB OTA application slots;
- a large LittleFS partition for robot assets;
- size-optimized firmware settings.

Build reports include component size and memory use. Camera buffers, audio
queues, prepared motion plans, networking, storage, and OTA checks share limited
resources.

The September 2 [build reference](https://docs.google.com/document/d/1JZMMG3J96v6cnw2YupPp9OF9fiw0H4j0tS8t8fsplJk/edit)
and S3 pin map agree on these assignments:

| Function | GPIOs |
| --- | --- |
| Eight servos | 1, 2, 14, 21, 47, 48, 45, 46 |
| OLED | SDA 0, SCL 43 |
| Battery ADC | 3 |
| SD card | CMD 38, CLK 39, DAT0 40 |
| I2S audio | Microphone 19, amplifier 20, BCLK 41, WS 42 |
| Octal PSRAM | 33–37 reserved |

These pins are specific to V1. The planned P4 port needs its own allocation and
bench tests; see the [V2 roadmap](/posts/ainekio-v2/).

## Setup and configuration

Initial setup uses the `Ainekio-Setup` WPA2 access point and a stable per-device
key. The owner joins that network and supplies Wi-Fi and gateway settings through
a local form.

Network settings use two storage slots. New settings are written and validated
in the inactive slot before it becomes active. A failed write leaves the previous
settings selected. Network resets preserve calibration, poses, and ADC settings.

## Motion

Eight MCPWM channels drive the servos. Motion data is prepared before playback;
named assets and `motion_plan_v1` frames use the same calibration, angle limits,
stop, fail-safe, buffer, and timing checks. Plans allow at most 32 frames.

The library includes stand, rest, a held sit pose, walking, turns, wave, bow,
`curious`, and dances including Macarena and salsa. `curious` looks right and
left before returning to its starting pose. Named 45°, 90°, and 180° turns remain
open-loop estimates until measured on the assembled robot.

Playback eases between targets. V2 will need twelve-joint assets and matching
validators, plus its planned per-joint calibration,
inversion, limits, acceleration control, and staged startup.

## Camera and microphone

The OV3660 takes XGA stills after requests or selected events. Operator preview
is limited to QVGA/VGA and starts disabled. The fast capture profile uses short
manual exposure for indoor 60 Hz lighting, moderate gain, denoise, neutral
sharpening, and no auto-exposure settling delay. It replaced a higher-gain
profile that produced cross-hatch artifacts.

Motion and utterance completion can request a still tagged with the originating
event's ID. For motion, the JPEG precedes the terminal result. A snapshot failure
is reported separately from a motion that already completed.

Microphone capture is 16 kHz mono PCM. A pinned neural voice activity detection
(VAD) model closes utterances using minimum-duration, silence, and maximum-duration
limits. A PSRAM queue absorbs short network stalls.

The microWakeWord/TensorFlow Lite Micro runtime loads a versioned local model
package and validates its manifest and tensor format before reporting readiness.
No accepted production Ainekio weights are tracked, so the initial configuration
leaves wake detection unavailable. See [camera feedback](/posts/vision-loop/)
and [listening and speech](/posts/voice-loop/) for the complete paths.

## Speaker, storage, and recovery

Speaker PCM is accepted during an explicit TTS burst, queued, and sent over I2S.
Overflow, interruption, data outside a burst, and completion have explicit
protocol results.

LittleFS stores versioned motion, face, PCM, and wake assets. SD logging uses a
low-priority task and limited rolling logs. OTA images must pass gateway
authentication before rollback validation marks the boot healthy.

Transport loss stops normal operation and starts limited reconnect attempts.
Stale control traffic stops active motion while allowing an authenticated idle
session to remain connected.

## Testing still needed

Portable-core tests, protocol fixtures, firmware policy tests, ESP-IDF builds,
application/LittleFS flashes, and digest readback have checked code and installed
images. Physical testing must establish servo alignment, battery performance,
microphone acoustics, speaker continuity, camera quality, and stability when
motion and media run together. [Current Status](/posts/current-status/) records
the dated results and remaining work.
