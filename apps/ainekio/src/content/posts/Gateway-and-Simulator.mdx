# Connecting and inspecting the robot

Ainekio's `Master/` code connects MetaHuman to the body. It contains the
authenticated gateway, operator dashboard, and Environment adapter. The gateway
handles robot sessions and media; the adapter translates MetaHuman actions into
robot commands and returns their results.

MetaHuman schedules work and reviews objectives. The body controller enforces
motion safety.

## Gateway

The gateway authenticates the robot and adapter separately. Robot sessions report
identity, capabilities, readiness, state, and command results. The gateway handles:

- protocol-v1 JSON control and binary media frames;
- command sequence IDs and waiting for terminal results;
- translation of features and readiness into available actions;
- camera metadata and JPEG delivery;
- microphone utterance assembly and paced speaker PCM;
- connection epochs, errors, media counters, and operation telemetry.

Local discovery uses DNS-SD with a limited attempt at a cached endpoint. Stale
cache entries are not permanent configuration. Local mode does not automatically
switch to the optional relay.

## Dashboard

The dashboard shows body state, camera/wake readiness, battery classification,
media counters, and connection state. Operators can enable limited camera preview,
change microphone or wake settings, request supported actions, and run hardware
checks such as a speaker test tone.

The dashboard volume setting affects that test tone. It does not change ordinary
MetaHuman speech volume. Displayed hardware state comes from the robot and gateway.

## Environment adapter

The adapter implements MetaHuman's generic Environment Bridge interface. It
advertises what the selected body can currently do and translates actions:

| MetaHuman action or event | Ainekio path |
| --- | --- |
| `robotCommand` | Checked named command |
| `robotMotionPlan` | Frame plan, if supported by the body |
| `captureImage` | Fresh snapshot and matching JPEG |
| Robot speech | Rendered PCM sent through the gateway |
| Microphone utterance | VAD-ended WAV sent to MetaHuman Whisper |

Action results wait for robot feedback, including playback feedback for speech.

September work adds SQLite action records and pending result/observation delivery.
An action ID is tied to its request content. Repeated delivery can return its
existing record instead of running the physical command again. Dispatch checks
the Coordinator's current body ownership, and cancellation can block an original
request that arrives late.

If dispatch may have happened but its outcome is missing, the adapter reports
that uncertainty for recovery. These adapter, gateway, and test changes are local
uncommitted work supporting the [MetaHuman redesign](/posts/metahuman-integration/).
Crash recovery and physical stopping still need deployed tests.

## Retired simulator

The simulator experiment was unsuccessful and has been completely retired.
It is outside the current tooling and V2 plan. The
[July motion article](/posts/archive/motion-systems/) retains its design,
command mappings, and reported tests as history.

## Transport results and next tests

Physical tests have produced authenticated sessions and completed commands.
They have also recorded abnormal WebSocket closes and host `No route to host`
errors while the gateway remained running.

The cause of those connection losses is unresolved. Strong Wi-Fi signal alone
cannot exclude incomplete binary writes, routing failure, controller reset,
power faults, or WebSocket lifecycle errors.

The next diagnostic run should record robot errors, connection epochs, media
counters, reset reason, host routes, and gateway operations together. Change
retry behavior one variable at a time so the results remain interpretable.
