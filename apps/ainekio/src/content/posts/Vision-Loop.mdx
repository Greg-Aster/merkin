# Pictures tied to actions

Ainekio takes still images when requested, after selected movements, or when a
spoken utterance ends. Each image carries an ID linking it to the event that
requested it. MetaHuman uses these images for perception. Continuous room video
is not sent to the model.

The dashboard can enable a low-rate preview for an operator. Preview starts off.

## Camera settings

The current S3/OV3660 path captures XGA JPEG stills. Preview is limited to QVGA
or VGA at a capped requested rate. It uses one PSRAM framebuffer and leaves the
capture engine idle between frames to limit memory and bandwidth use.

The fast capture profile uses:

- short manual exposure for common indoor 60 Hz lighting;
- moderate gain, denoise, and neutral sharpening;
- no automatic-exposure settling delay;
- JPEG quality chosen to retain detail within the payload limit.

An earlier high-gain, sharpened profile produced cross-hatch artifacts. Reducing
gain and removing sharpening improved the capture. The planned P4 body still
needs its own camera and communication integration.

## When a picture is taken

| Trigger | Image identifier |
| --- | --- |
| MetaHuman or dashboard snapshot request | Request ID |
| Completed motion | Command sequence ID |
| Voice activity detection (VAD) closes an utterance | Robot-generated utterance ID |

For a motion snapshot, camera metadata and the JPEG are sent before `done`.
For an utterance snapshot, the shared ID lets MetaHuman join what was heard
with what was visible.

Images travel through the gateway, Environment adapter, and Environment Bridge.
The resulting context includes frame identity, its action or utterance ID,
capabilities, and current body state. The saved workflow can wait for that
specific result and image.

## Checking a visual goal

Suppose the request is “Walk until there is enough light.” A completed `walk`
establishes that the command ran. A fresh image is needed to decide whether
the robot reached a brighter place.

MetaHuman represents this with a `visual_observation` completion requirement.
A command-only objective can use `action_result`. Action Result and Goal Review
evaluate the returned evidence and decide whether to finish or continue.
An inconclusive image may lead to another validated action.

September workflow code handles results and images arriving in different orders.
Rejected, expired, or cancelled actions can return for review without waiting
for a picture from a movement that never happened. Controlled workflow tests
cover those cases; real camera quality and visual goal completion still need
physical testing.

## Current limits

Ainekio does not advertise target-relative navigation or visual approach. A
`findObject` concept elsewhere in MetaHuman does not provide the robot with
object localization or approach behavior.

Earlier Active View research explored detection and temporal segmentation. It
remains outside the current production path; tracking a detection does not by
itself establish an object's identity or satisfy a goal.

## Next physical test

Repeat a visual objective while recording the accepted task, required result,
action ID, robot acknowledgement, terminal result, and matching fresh image.
Each review should identify the frame used to judge the goal. If the condition
is absent, continuation should remain limited; completion should occur only
when a later image establishes it.
