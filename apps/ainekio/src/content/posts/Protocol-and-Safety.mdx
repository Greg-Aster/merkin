# Commands and results

Ainekio protocol v1 carries JSON control messages and binary camera/audio frames
between the gateway and robot. The firmware, gateway, and tests use the
same contract for authentication, message IDs, capabilities, payload limits,
and command results. Malformed commands are rejected before execution.

## Requesting movement

MetaHuman requests named actions such as `wave`, `bow`, `sit`, or `turn_left_45`,
or submits a checked `motion_plan_v1`. The body core translates commands into
authored motion assets and calibrated joint movement.

```text
Supported action -> protocol checks -> body checks
  -> prepared motion -> execution -> result with the command ID
```

Motion plans have limits on frame count, fields, duration, and joint ranges.
They use the same stopping and fail-safe behavior as named motions. Model output
cannot write directly to servo PWM.

The current contract has eight joints. V2 must update joint names, calibration,
assets, validators, and advertised capabilities together
before accepting twelve-joint plans. See the [V2 roadmap](/posts/ainekio-v2/).

## Command states

| Result | Meaning |
| --- | --- |
| `ack` | Accepted for execution |
| `done` | Robot-side action completed successfully |
| `cancelled` | Accepted work stopped before success |
| `nak` | Rejected as invalid, unsafe, or unsupported |

A successful socket write only confirms delivery to the local transport.
`ack` confirms robot acceptance; `done` confirms command completion.

An objective may need more evidence. For “find better light,” a finished walk
must be followed by a fresh image showing whether the light improved.
MetaHuman uses `action_result` for command-only goals and `visual_observation`
for visual goals. Other goals can depend on user input or environment state.
Action Result and Goal Review evaluate this evidence in the saved execution;
Robot Status displays progress.

## Capabilities and media

The body reports supported features and current readiness. The gateway translates
them into the actions MetaHuman can select:

- camera requests require a ready camera;
- wake-gated microphone requests require an accepted, ready wake model;
- motion plans must be advertised by the connected body.

MetaHuman's output schema uses those current actions and command names.

JSON carries control state and media metadata. Binary frames carry JPEG,
microphone PCM, or speaker PCM with a small type/counter header. Camera metadata
can identify a motion, utterance, or explicit snapshot request. A completed motion
can send that metadata and its JPEG before reporting `done`.

## Stops and connection loss

Application control pings keep idle sessions alive. A short gap in valid control
traffic stops active motion without disconnecting a healthy idle session.
WebSocket, gateway, or Wi-Fi loss enters fail-safe/offline behavior and starts
limited reconnect attempts.

Other controls include duplicate detection, message IDs, fixed media-size limits,
limited command/media queues, joint calibration, interruption and stop precedence,
and explicit microphone/TTS burst state.

Ainekio's movement is body-local and open-loop. Named turns and motion plans
do not supply localization or feedback relative to a target.

## Recovery work

September adapter changes retain action IDs, dispatch records, terminal results,
and pending feedback. They reject reuse of an ID with different content and
check which Coordinator instance currently controls the body. A stale instance
must not issue a new action.

If a restart leaves a command's outcome uncertain, the adapter reports
`outcome_unknown`. This is an adapter result, separate from robot protocol states.
Recovery must reconcile it before deciding whether another movement is safe.
The receipt work is under local integration; disconnect, cancellation, and
restart behavior still need deployed robot tests.

## Next fault tests

- Lose the connection during each class of motion.
- Cancel at different points in an eased transition.
- Send malformed or duplicate media metadata.
- Fill camera or speaker queues while moving.
- Restart the controller or trigger OTA rollback during an interrupted session.
- Reconnect repeatedly and check that old commands are not replayed.

Source tests cover the protocol and shared body core. The
[status report](/posts/current-status/) separates those results from tests on
the assembled robot.
