# Meet Ainekio

*Cover: AI concept artwork based on the September 20 Blender assembly. The build
journal includes the actual Blender views and prototype photographs.*

Ainekio is a small, owner-built, four-legged robot with a camera, microphone,
speaker, and a face on a small display. The project explores a robot companion
that can talk, observe its surroundings, and act on a request.

Two systems make that possible. The computer on the robot controls its motors
and checks movement limits. [MetaHuman OS](https://github.com/Greg-Aster/metahuman-os),
a separate software project, provides conversation, memory, reasoning, and
speech services. The connection between them lets a conversation lead to an
action, then brings the result back into the conversation.

That is the project’s direction, with parts still under development. The current
robot has demonstrated motion commands and audible playback. Reliable repeated
conversations and requests that combine reasoning, movement, and observation
still need testing on the revised system.

## Project intent

The aim is a **robot familiar that grows and learns**. Conversation, memory,
perception and physical action should stay connected. Ongoing work should
respond to fresh input rather than depend on isolated turns. This is an evolving
goal; implementation evidence and physical test results remain distinct.

## The current robot and its successor

The working body is **V1**. It has eight MG90S servos: small motors that move to
chosen angles, with two serving each leg. An ESP32-S3 controller runs scripted
poses and movement sequences.

**V2** is a substantially different twelve-servo design with sideways leg
placement and an ESP32-P4 controller. Continuous Walk, Run, Crawl and
six-direction Crab share the gait controls; 23 finite gestures have a separate
saved speed multiplier. Revised gait geometry and controller deployment are
recorded in the journal; loaded walking remains to be measured.

**October 6: the printed V2 chassis could not stand on its MG90 servos.**
The LCD and shell pieces have not been printed. After researching alternatives,
Greg is keeping the servos, removing weight in Blender and revising the legs.
New parts are still printing; the lighter assembly has not been tested.
Roughly 20% less weight and 20% more lifting force are current owner estimates.

The heavy **10,000 mAh battery-bank approach has been dropped** in favor of
separate batteries and onboard charging circuit boards. Exact cells, boards,
capacity and runtime are not established in this update. Earlier Anker and
SHARGE packaging studies remain in the dated build history.

Wireless, with the Q6A offboard over Wi-Fi, is the current priority. Wired
retains the onboard-Q6A/native-USB alternative. The P4 IMU estimator is now
implemented, while live acquisition, balance correction and the robot ROS 2
adapter remain integration work. Continuous steering and camera/recognition
interfaces have progressed; sustained wireless reliability remains unresolved.

## Why the software is changing too

A short command such as “stand” has a clear end. A broader request may take
several actions and pauses. The software needs to remember what was requested,
which steps have finished, and what it is waiting for.

MetaHuman’s redesign saves that progress in a **workflow**: a sequence of software
steps that can pause for a result and continue afterward. Saved requests retain
user corrections and results from specialist software workers. A September 8
live review found the revised workflows running with robot feedback, camera
images, and speech-delivery acknowledgements.

That run also exposed stale goals and repeated influence from unresolved
intentions. Later source repairs keep finished work out of the active-goal
display and require optional Desire-driven robot work to follow a finite,
reviewed plan with an observable outcome. Ainekio’s gateway work separately
keeps delayed command results connected to their original request without
repeating movement during recovery. Controlled tests cover these repairs;
the complete revised system still needs deployed and physical validation.

## How a request reaches the body

For a simple example, consider a request to stand:

1. MetaHuman’s **Work Coordinator** decides when the request can run. Its
   workflow selects an action supported by the connected robot.
2. The **Environment Bridge**, MetaHuman’s connection to external devices, passes
   the request to Ainekio’s **adapter**, which translates it into the robot’s
   command format. An authenticated **gateway** carries it to the body.
3. The controller checks the command and moves the joints within their limits.
4. The result travels back to MetaHuman so it can continue or finish the request.

A broader goal needs another check. For example, a future request to move into
better light would require a new image afterward. A completed movement alone
would not show whether the lighting improved. This distinction guides the
[software integration](/posts/metahuman-integration/) and
[camera work](/posts/vision-loop/); it is not a claim that this example has
passed a physical test.
