# Robot Systems

<p className="ainekio-system-note">This page is the working system map for Ainekio. It keeps the top-level architecture visible while the older detailed notes remain available as linked references.</p>

The robot is split into two primary trees: **OS** and **Body**. OS is the remote or local intelligence layer that understands goals, language, memory, tools, and environment actions. Body is the physical or simulated robot layer that receives safe semantic commands, reports state, and owns hardware limits.

## OS

The OS side should stay responsible for high-level intelligence. MetaHuman OS can run on a more capable computer than the robot body, which keeps the first physical prototype smaller and avoids pushing heavy speech, vision, and reasoning workloads into a tiny servo body too early.

<p className="ainekio-doc-label">Current OS responsibilities</p>

| System | Job | Notes |
| --- | --- | --- |
| MetaHuman OS server | Main brain, UI, API, and graph runtime | The development server is the place where conversation, memory, tools, and environment actions meet. |
| Conversation and agents | Interpret user intent and choose tools or graph flows | This is where general interaction should live, not in the servo controller. |
| Speech services | Own STT/TTS unless moved later | Body-side audio can capture and play sound, but heavy processing should remain OS-side for now. |
| Environment Mode | Convert language into typed robot actions | The robot receives semantic actions, not raw servo angles. |
| Environment bridge | Stream commands and receive body state | The current path is event-driven rather than polling. |

## Body

The body side is the robot-specific execution layer. It should be able to say what it can do, refuse unsafe actions, translate safe commands into simulator or hardware motion, and report what happened.

### Software

The body software has three current targets:

1. Make the simulator loop reliable before physical servos move.
2. Keep command translation explicit and safe.
3. Preserve a clean path from virtual backend to real hardware backend.

### Hardware

The hardware tree is still a design target rather than a frozen purchase order. The important split is between logic power, servo power, command/control, sensing, and body packaging.

<p className="ainekio-doc-label">Hardware groups</p>

| Group | Contents |
| --- | --- |
| Body frame | Sesame-style reference body or a custom Ainekio body derived from the same expressive small-robot goals. |
| Controller | ESP32-S3, XIAO ESP32S3 Sense, Radxa Zero 3W, or a paired SBC plus microcontroller path. |
| Servo bus | Direct PWM only if pin pressure and timing are acceptable; PCA9685-style bus is the cleaner expandable path. |
| Servo rail | Dedicated 5V rail sized for multi-servo load, with common ground and safe distribution. |
| Sensing | Camera, microphone, OLED, battery telemetry, and possible distance/bump sensors. |
| Audio | Microphone, I2S amplifier, speaker, and speech handoff to MetaHuman OS. |

The current detailed hardware article is [Parts Overview](/posts/robot-familiar-parts-overview/). That page should remain the parts and purchasing detail owner while this page stays the higher-level system map.

## Working Rule

The OS should request named robot actions. The body should decide whether the action is safe, translate it into simulator or hardware commands, and report the result. Raw servo angles, calibration commands, and direct debug controls should stay out of the AI-facing command surface.
