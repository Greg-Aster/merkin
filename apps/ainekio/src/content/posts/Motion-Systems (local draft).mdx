# Ainekio Motion Systems - Investigation and Plan

The robot body is based on the Sesame bot, but running a Raspberry Pi (likely a Pi Zero 2 W) instead of the stock ESP32. The existing motion system is ESP32 firmware, so the job is to understand what that firmware actually does, then plan a new motion module and related systems that run on Linux. Unusual constraint: this will run in a virtual environment first and get rigorously tested before it ever touches the chassis.

## What the existing ESP32 system currently shows

There are two source tracks that must not be blurred together:

- Prior upstream research on the official Sesame robot firmware and companion app indicated a fuller ESP32 firmware with HTTP command/status endpoints, face assets, a captive portal, and a Python companion app.
- The local simulator checkout reviewed during this pass contains a simulation sketch at `sesame/sesame.ino`, movement data in `sesame/movement-sequences.h`, a generated `docs/robot.urdf`, and mesh assets under `docs/mesh` and `onshape`. That local checkout is useful evidence for servo order, sequences, the URDF body, and simulator assets, but it does not by itself prove the official HTTP API contract.

The checked simulator sketch is Arduino-ESP32 and uses `ESP32Servo.h` with eight servos. It defines the Sesame distro board pinout, subtrim values, `frameDelay`, `walkCycles`, and `motorCurrentDelay = 20` ms. The movement header defines the servo order as `R1, R2, L1, L2, R4, R3, L3, L4` and implements pose/animation functions as direct `setServoAngle(...)` calls with delays and loops. That makes the motion system pose/keyframe playback, not realtime gait kinematics. For the Python port, the first real movement content should come from translating those pose functions into sequence data, not inventing a new gait engine.

The HTTP API claim needs a source check before it becomes a hard contract. Prior research says the stock firmware exposes semantic commands over endpoints such as `/api/command` and `/api/status`, with command names like walk, dance, wave, swim, pushup, bow, shake, idle, stop, and rest. The simulator sketch I checked uses serial/debug command routing and commented server hooks, so the exact target firmware and companion repo still need to be re-read before `esp32-http` is treated as implemented architecture.

Useful details that are locally supported now:

- Brownout/current staggering is real in the simulator sketch: every servo write delays through `motorCurrentDelay`.
- Subtrim, per-servo angle commands, frame delay, and walk-cycle tuning exist in the simulator sketch or adjacent simulator tooling and are good references for a future tuning UI.
- The browser simulator source includes robot geometry: URDF plus STL/OBJ mesh assets. The Megameal side now uses that path: the simulator URDF and Onshape STL parts are converted into avatar-owned GLB meshes for the visible Ainekio/Sesame player avatar.
- ESP32Servo is a dependency of the simulator sketch, but the exact official firmware version pin and any version-specific servo bug should be reverified against the target firmware docs before this project relies on that detail.
- Any stock HTTP API should be treated as trusted-local-network only unless the verified firmware proves otherwise. The Ainekio bridge remains the outward boundary.

## Three architecture options

**Option A - keep the ESP32 as the motion controller.** Pi rides onboard for senses and network, ESP32 keeps running stock (or lightly modified) firmware, Pi sends commands to it over the verified stock API or serial. Least motion work, keeps proven movement sequences and the brownout stagger, and gets servo/logic rail separation for free since they're separate boards. Cost: two boards in a small body, and the ESP32 firmware becomes a dependency.

**Option B - full Pi replacement.** Pi Zero 2 W + PCA9685 servo bonnet, motion layer rewritten in Python. One board stack, full ownership, everything in one OS. Cost: the motion module has to be written, and Linux is not a realtime OS - though keyframe playback at Sesame's animation speeds doesn't need hard realtime, and the PCA9685 generates the actual PWM in hardware, so timing jitter on the Pi side only affects when a pose starts, not the pulse quality.

**Option C - all-in-one on a bigger Pi.** Pi 5 class board, everything onboard including possibly local STT/TTS and vision models. This is the "powerful raspberry pi" future case. Same motion module as Option B - which is the point. If the motion module is written properly, A/B/C are deployment choices, not rewrites.

Current lean: build the motion module as if Option B is the target, but keep the semantic command vocabulary close to the stock system so Option A can still work as a fallback during hardware bring-up. The exact ESP32 transport is not locked until the target firmware API is reverified.

## Efficiency and where processing lives - undecided, for consideration

For motion alone, the ESP32 is the better tool. Microcontroller, hardware-timed PWM, no OS in the way, tiny power draw, instant on. The Pi runs full Linux, draws roughly 0.6-3w, boots in ~30 seconds, and the OS can interrupt timing. If Ainekio were only a walking robot, the Pi swap would be strictly worse.

But the ESP32 fundamentally cannot contain STT, TTS, or vision understanding - a few hundred kb of ram, no meaningful ML acceleration. What an ESP32 *can* do is capture and forward: I2S mic streaming raw audio over wifi, ESP32-CAM style JPEG frames, and newer S3 chips can do wake-word detection onboard. Transcription, speech synthesis, and image understanding have to happen somewhere bigger - onboard SBC or across the network.

That gives three honest placements (overlapping with but not identical to the architecture options above):

- **ESP32 captures and forwards everything, no Pi at all.** Mic and camera stream over wifi straight to MetaHuman OS, which does all STT/TTS/vision. Cheapest, lightest, most power efficient, and the intelligence already lives off-board by design - so this is a legitimate minimal v1, not a hack. Costs: robot is completely helpless offline, constant raw streaming eats bandwidth and battery, and ESP32 audio quality/latency is mediocre.
- **Pi only** (the current parts list). One board owns motion, senses, and network. The Python-servo inefficiency is mostly handled by the PCA9685 doing the actual PWM in hardware - the Pi just sends target angles over I2C. Perspective on power: 8 MG90S servos spike at 10-20w when moving; the Pi's 1-3w is noise next to that. The Pi only really costs battery at idle, which sleep states can address.
- **Both boards.** Microcontroller does realtime motion and reflexes, SBC does perception and network - this is the standard pattern in real robotics (drone flight controller + companion computer), not a compromise. ESP32 keeps its proven firmware, stagger, and instant-on safety; Pi handles camera, mic, speaker, and the bridge, and commands the ESP32 over the verified stock API or serial. Costs: two boards in a small cavity, two power consumers, two codebases to maintain.

STT/TTS placement specifically: OS-side only is the right call for the Zero 2 W. Local STT on a Zero (Vosk small model) is possible but sluggish, Whisper is painful, Piper TTS runs but slowly. Sane split for now - wake word onboard (cheap), everything else in MetaHuman OS. Onboard speech becomes realistic on Pi 5 class hardware, which is Option C territory.

None of this is decided. The motion module design doesn't force the choice - a verified ESP32 passthrough backend covers the two-board path, the pca9685 backend covers the Pi-only path, and the forwards-everything path skips the motion module's hardware backends entirely and just uses stock firmware.

## The motion module plan

A Python package, provisionally `ainekio-motion`, in three layers with swappable backends - same trick as the MetaHuman interface nodes.

**Command surface (top).** Speaks semantic robot commands rather than raw servo angles. The preferred compatibility target is the stock firmware contract once the exact `/api/command`, `/api/status`, command-name, and face-name details are reverified. The Ainekio bridge connects here. Probably add a WebSocket alongside HTTP for outbound telemetry (battery, pose state, heartbeat) since the overview doc already wants that.

**Sequence engine (middle).** Loads keyframe/pose sequences and plays them: pose timing, walk cycles, and the servo stagger for current management. First sequences come from porting `movement-sequences.h`; the local simulator copy shows direct pose functions and servo angle calls, so this is translation, not invention. Sesame Studio's slider/capture workflow could eventually export straight to the Python format instead of C++. Also owns the safety behaviors from the overview doc: stop always wins, movement duration limits, refuse commands below battery threshold.

**Servo backend (bottom).** An interface with at least three implementations:

- `pca9685` - the real one, driving the Adafruit bonnet over I2C
- `virtual` - no hardware, publishes joint angles as data so the virtual environment can consume them
- `esp32-passthrough` - deferred passthrough that forwards commands to a stock Sesame over the verified stock transport, likely HTTP if the prior API research checks out, or serial if that is the safer bring-up path

The virtual backend is what makes "rigorously tested before it touches the chassis" real. The same sequence engine that will drive metal runs headless, and its joint output can drive the simulated articulated body.

## Virtual environment fit

This connects to the Step 1 bridge work. The Megameal environment bridge already moves observations and semantic actions between MetaHuman OS and a body. The motion module slots underneath: MetaHuman sends `walk` through the bridge, the motion module's sequence engine plays the walk keyframes, and the virtual backend emits joint angles.

Staging inside the virtual environment mirrors what the Step 1 doc already says: conversation-only first, then wasd-style movement (which maps to command-level motion - walk, turn, stop - no joints needed), then a virtual body with actual servo points and joints driven by the sequence engine. That last stage is where the motion module gets its real testing, because the exact keyframes that will move the physical servos are what drive the virtual body. The Megameal avatar with jointed legs is the test rig, and for the Sesame simulator the body should move from physics contact rather than root-motion displacement.

The Megameal side has now taken the literal robot-body path. The Sesame simulator URDF is converted into one GLB per simulated rigid body, and those meshes attach to the same chassis, leg, and foot bodies that the physics rig moves.

## Implementation progress

Started the first motion-module slice in the Ainekio robot repo at `/home/greggles/Ainekio/motion`. The work is intentionally repo-local for now: no Megameal, MetaHuman OS, or Sesame simulator source edits until those decisions are made separately.

Current implemented pieces:

- Semantic robot command model, with no raw servo-angle API for AI callers.
- Virtual joint telemetry path for simulator adapters. The current Ainekio code still carries `RootMotionIntent` fields from the earlier adapter plan; that is now compatibility debt for the Sesame simulator path. The Megameal robot simulator is taking a literal physics approach: servo targets move articulated bodies, and contact with the world generates displacement.
- TTL-aware reconnect catch-up helper. It can do a one-shot reconnect read, but expired actions are discarded so stale movement is not replayed.
- Safety controller with e-stop latch, low-battery lockout, lease expiry, stale-command stop, and offline idle fallback.
- Sequence engine with provisional Sesame servo names, basic built-in sequences, angle clamping, and per-servo start staggering for brownout/current management.
- Virtual backend that emits joint telemetry for a future Megameal adapter. It currently preserves the legacy root-motion field in telemetry, but the Megameal Sesame adapter should ignore or remove that path rather than using it for locomotion.
- Disabled physical backend guard that refuses hardware actuation unless hardware is explicitly enabled in config.
- JSON config loader and `config.example.json` for bridge URL, ports, backend, telemetry, and safety settings so destinations do not become hardcoded constants.


The important boundary decision from this slice: the motion module owns the robot-body behavior and physical safety, but Megameal owns the virtual physics simulation. Joint telemetry is the bridge data. For the literal robot simulator, Megameal should not fake movement with root motion; it should let the servo-driven body interact with the world and move from physics.

## Megameal-side simulator progress

Megameal now has the player-avatar side of the simulator working as a visible, articulated robot body. The selected avatar is `player_avatar_ainekio_sesame`, not the older ball-of-light default. That avatar activates the `ainekio-sesame` physics rig and uses GLB robot meshes generated from the Sesame simulator URDF. The old generic square/player mesh is no longer the Ainekio/Sesame render path.

The current Megameal-side data flow is:

1. Avatar selection loads the Ainekio/Sesame player avatar package.
2. The runtime registers the Ainekio/Sesame articulated physics rig.
3. The rig spawns one chassis body, four upper-leg bodies, and four foot bodies.
4. Each body has a simplified collider for simulation and a visible GLB robot mesh for rendering.
5. Servo target events use `servo-target-json-v1`.
6. The DEV-only game bridge can submit a generic `submitMotionEvent` command to the running game.
7. Master Control exposes Megameal-owned neutral and step-cycle test buttons that send registered preset IDs through the bridge; the installed level package resolves those IDs to avatar-owned Ainekio/Sesame motion events on the runtime side.

This makes Megameal end-to-end compatible on its side: a motion event can be created in Megameal, resolved through the installed player/avatar package, sent through the dev bridge, queued in the runtime, applied to the eight servo joints, and rendered on the visible robot body. The Ainekio-side adapter is still future work and should connect to the same `servo-target-json-v1` shape without changing the Ainekio motion module's internal output format.

Important limitations:

- The current Megameal test sequences are simulator harness motions, not the final physical movement library.
- The colliders are simplified proxies sized to the generated meshes; they are not triangle-mesh servo bodies.
- The Megameal bridge command validates generic motion event shape, but the future Ainekio adapter still needs to translate Ainekio virtual backend output into the Megameal event path.
- No root-motion displacement is used for the Ainekio/Sesame robot. Any body movement should come from servo-driven physics contact.

## STT, TTS, vision, sensors

Not motion, but the plan has to leave room:

- STT/TTS - currently supported OS-side only (MetaHuman does the talking). Onboard is possible later, more likely on Option C hardware than a Zero. The motion module should not own speech; speech/text and audio output belong to a separate audio service.
- Vision - undecided between a full camera and ultrasonic sensors. These are different jobs: the camera is for the brain (observations up the bridge), ultrasonic is for the body (local reflexes - don't walk off the table, stop before the wall). Could be both. Ultrasonic reflex handling belongs in the motion module's safety layer since it has to work without the network. Camera does not belong in the motion module at all.
- Sensor data goes up the same telemetry channel as battery and pose state.

## Megameal simulator progress - literal servo physics

The Megameal simulator foundation is now started in `/home/greggles/Merkin/apps/game.megameal`. This is separate from the Ainekio motion module. The Ainekio module remains the planned real-world robot motion module; Megameal gets a separate adapter/simulator layer so game requirements do not reshape the physical robot API.

Current simulator direction:

- The selected avatar can reference an articulated physics rig.
- The Ainekio/Sesame rig lives beside the player avatar data, not in generic game code.
- Generic articulated-rig code lives under `src/game/physics-rigs` and is data-driven so future robot dimensions, body counts, and servo layouts can change without rewriting the engine.
- Engine physics now supports generic revolute joints and motor position targets through the physics adapter contract.
- Rapier implements those joints behind the adapter boundary. Game code does not import Rapier directly.
- The current Sesame rig is a primitive-collider physics body: one dynamic chassis plus eight limb/foot bodies connected by eight revolute servo joints.
- Movement is literal simulation, not root motion. Servo target angles drive the joints; friction and collision with the world are what should eventually move the body through a room.
- The existing ball-of-light avatar remains selected by default. The Sesame physics rig is present as a selectable avatar entry, and the Master Control Player Package panel can now edit the selected avatar through the player avatar package file.
- The future Ainekio-to-Megameal adapter should emit stable servo-target events shaped like:

```json
{
  "schemaVersion": 1,
  "robot": "ainekio-sesame",
  "sequence": "walk",
  "command": "walk",
  "issuedAtMs": 0,
  "ttlMs": 250,
  "frames": [{ "servo": "R1", "angleDeg": 30, "atMs": 50 }]
}
```

Known remaining simulator work:

- Build the Ainekio-side Megameal adapter that reads Ainekio motion-module output and submits `servo-target-json-v1` events into Megameal. The adapter should translate or ignore Ainekio's legacy root-motion fields rather than using them to move the Sesame body.
- Tune the primitive rig so servo commands produce stable locomotion in the virtual room.
- Import or convert the Sesame visual model from the simulator URDF/mesh asset path and attach visuals to the primitive physics bodies after license and provenance are cleared.
- Verify the simulator live in Megameal with the Sesame avatar selected.
- Add battery, face/OLED, and offline fallback behavior to the adapter path without moving physical safety out of the Ainekio motion module.
