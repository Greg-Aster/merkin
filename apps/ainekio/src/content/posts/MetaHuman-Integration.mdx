# Keeping track of a robot request

MetaHuman's September redesign saves each objective with its workflow progress.
A request can wait for a robot result, call a specialist, receive a correction,
or resume after restart without rebuilding the task from a conversation summary.

This is development code with focused test results. Deployment and repeated
physical operation still need validation.

## Saved execution

The graph runtime uses LangGraph to schedule editable workflows. A SQLite store
for the selected profile retains the objective, ordered events, immutable node
outputs, versioned checkpoints, and actions waiting to be dispatched.

Child robot workflows share that execution. Finite specialist agents run as
Work Coordinator jobs and return results linked to the parent request. A plan
can remain saved while later stages wait, retry, or continue.

Robot Status displays the saved execution's decisions. Conversation buffers
provide recent context, and memory supports recall. The execution record now
retains the objective, replacing the previous guide's Environment Task State
description.

## Sending an action

The Work Coordinator accepts finite jobs and manages their lifecycle, recovery,
and access to the body. The execution store records intended work; the
Coordinator schedules it and records acceptance.

Environment Bridge Out saves dispatch intent with the graph checkpoint. The
Environment Bridge maintains the external connection. Ainekio's adapter
translates the selected action into the robot protocol.

Local adapter changes retain action records across interruptions. They reject
an action ID reused with different content, check current body ownership before
dispatch, and redeliver acknowledgements/results without issuing another command.
If a physical outcome is uncertain after interruption, recovery must reconcile
it before deciding on further movement.

## Decisions and review

The orchestrator routes input as a new request, a correction, or cancellation.
The Environment Action Selector can choose conversation, a supported body
action, or generation of a limited motion plan. Parsing and body checks constrain
the result.

```text
Accept request -> start or resume saved workflow
  -> select and validate action -> save dispatch intent
  -> Coordinator -> Bridge -> adapter -> body
  -> wait for result and observation
  -> Action Result -> Goal Review
  -> finish, wait for input, or continue
```

Action Result interprets feedback. Goal Review decides whether the objective
has been met. Both run within the same saved execution. Rejected, expired, or
cancelled actions can return without an image from a movement that never ran.
Visual goals require a current image linked to the action.

## Conversation and speech

Microphone utterances enter through Environment Bridge and Whisper. An image
with the same origin ID can join the turn. Conversation uses the same submission
and context handling as other MetaHuman interfaces.

Current context work preserves the latest user instruction within the configured
history window so intervening assistant actions do not crowd it out. The saved
execution separately retains the objective and its events.

Speech uses the configured synthesis and delivery services, then Bridge transport
and Ainekio's paced speaker output. Playback results, interruptions, and delivery
failures are tracked separately from synthesis and workflow completion. See
[listening and speech](/posts/voice-loop/).

## V2 and remaining tests

MetaHuman will continue requesting actions while the body changes from S3/eight
servos to P4/twelve. Current motion contracts have eight joints. V2 needs matching
joint names, assets, validators, capabilities, camera/audio support, and
communication before new movement is exposed.

The September review records tests of saved workflows, specialist returns,
steering, cancellation, retries, result ordering, and fresh-process resumption.
The providers were controlled fixtures; results apply to that recorded snapshot.

Remaining work includes migration coverage, deployed recovery, compatibility
between adapter and Coordinator, direct stop, and repeated physical runs.
[Current Status](/posts/current-status/) lists baselines and test counts;
[autonomy modes](/posts/bounded-autonomy/) describes how work starts without a
new user request.
